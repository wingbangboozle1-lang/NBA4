# Executive summary and decision register

**Snapshot:** 2026-11-14 UTC. **Decision status:** research/dashboard scaffold only; no NBA lines, picks, injury-minute projections, correlations, “skill” scores, leaderboard winners, or rewards are authorized or validated.

## Executive summary

The starting repository was essentially empty: a one-line README with no application, historical results, price feed, injury history, or model. I verified the current official NBA, GitHub, and Netherlands Gambling Authority sources and wrote a strategy/validation specification without inventing outputs.

The biggest blocker is not model choice. NBA’s own FAQ says its Stats are not downloadable for personal or academic use; NBA.com’s Terms further restrict use of NBA Statistics in connection with gambling, including legal gambling, and require express prior consent for certain comprehensive, regularly updated databases. This project therefore must not scrape NBA Stats or turn NBA Stats content into betting features/picks without written rights. The site is designed as a transparent evidence/decision dashboard and deliberately shows no picks until an authorized data contract, legal/product scope, point-in-time inputs, benchmark prices, settlement rules, and empirical gates are in place.

A “luck-free” strategy cannot be promised. The responsible target is to reduce leakage, overfitting, and small-sample noise and to display uncertainty. Correlations, bet values, injury effects, and rewards remain blank because there is no permitted historical dataset or tested model. GitHub Pages is static and is not permitted for a commercial SaaS/online business; it can publish an informational dashboard, but it cannot run a secure, live forecasting service. The Netherlands Gambling Authority’s guidance makes the product/reward/affiliate classification a legal question, not a fact this repository can answer.

**Immediate recommendation:** keep the public dashboard informational and explicitly unvalidated; do not publish or reward picks. First resolve data rights, product/jurisdiction/hosting and data feed. Then define a market, build a timestamped licensed-data ledger, preregister baselines/metrics/thresholds, run walk-forward and untouched-holdout tests, and enable strategy-specific output only after every gate passes.

Primary sources: [NBA Stats FAQ](https://www.nba.com/stats/help/faq) · [NBA.com Terms of Use](https://www.nba.com/termsofuse) · [GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits) · [Ksa remote-gambling guidance](https://kansspelautoriteit.nl/remote-gambling-act-force)

## Suggestions to discover the missing information (not implementation approvals)

1. **Rights-first source diligence.** Create a vendor/rights matrix for game/player statistics, player tracking/lineups, injuries, schedule updates, odds history/quotes, results and settlement. For each feed request written confirmation of betting use, derived work, automation, historical retention, redistribution and commercial terms. The current NBA Stats FAQ/Terms are a stop sign for an unlicensed direct-NBA Stats pipeline.
2. **Product/legal classification.** Write the product flow in plain language: who receives picks, whether a user can wager, whether the site sends users to an operator, whether advertising or an entry fee exists, how rewards are funded, and which countries are targeted. Ask counsel to map it to local rules, age controls, marketing limits, responsible-gambling requirements, privacy, consumer and prize/contest obligations. The Ksa’s web summaries say they are summaries; use the underlying laws/rules for decisions.
3. **Data feasibility proof.** After contracts, request a small permitted sample with identifiers, event timestamps, update history, historical coverage, price/settlement schemas and correction behavior. Test missingness, latency and rights labels before choosing a model or promising “no manual input.” Do not put vendor keys in the static website.
4. **Research preregistration.** Define one single-bet market, one player-prop market and one combo hypothesis; pick a simple baseline, a future holdout and uncertainty/power plan before testing. Keep the first leaderboard as a validation audit, not a reward ranking.
5. **Rotation and game-flow evidence.** Obtain point-in-time report snapshots and authorized lineup/minutes history. Measure uncertainty for status-to-availability, availability-to-minutes and minutes-to-production separately; do not treat a reported injury as a causal impact estimate.
6. **Hosting decision.** Keep GitHub Pages for an informational static dashboard only. If automated ingestion, private keys, account-level rewards, a commercial product or a paid service is intended, select compliant hosting and implementation architecture before adding live operation.
