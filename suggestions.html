Suggestions and decision queue

This page exists so the path can be chosen before anything is built. It merges two proposal sets written in parallel sessions and preserves both: the decision queue (four gating decisions plus twelve prioritised proposals with options and trade-offs) and the review register (23 proposals whose Decision column is deliberately empty — it is filled in by the reviewer, not by the agent).

i
Nothing on this page has been implemented.

Pick a path in the decision queue first, then open a request. Rows marked Needs decision / Blocked cannot be built before their dependency is closed. Suggested decision values: Accept, Reject, Defer, or a note. Editing this page is the approved way to change a proposal — do not implement a suggestion that still reads “Needs a decision”.

What we still need from you

Facts only the project owner can supply — no source can answer these.

Full question register →
  1. Intended use. Personal research, a public tipster page, or a commercial product with rewards?
  2. Budget for data. Licensed feeds are the gating cost; “free NBA stats” is not an available route.
  3. Jurisdictions. Which countries would see picks, and would any link to a bookmaker?
  4. Risk tolerance for being wrong. Whether a silent “no pick” is acceptable, or whether you need a measurable pipeline even before it is profitable.
  5. Timeline. Whether a correct empty dashboard now beats an attractive but unvalidated one later.

How to review

  1. Read the row and check the evidence link.
  2. Record Accept, Reject or Defer in the Decision column (or a note).
  3. Implement only the accepted rows, in the order agreed.
  4. Record the decision in the repository's coordination board so the change history stays traceable.

One rule for every suggestion

No suggestion may add a number that an official source does not support. Any value that cannot be confirmed from an official or authorised source stays blank and is flagged as unverified — that rule applies to the improvements as much as to the pages they would change. Where the two registers propose the same idea (for example P-10 and S-06/S-10, or P-11 and S-15), the overlap map in the register lets the reviewer accept one wording and reject the duplicate.
