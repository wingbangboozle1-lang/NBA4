Suggestions

This page exists so improvements can be reviewed and selected before any code, data or copy changes. Each entry states the problem it solves, the options, the trade-off, the effort and an official source for its factual basis. Suggested status values are Proposed, Needs a decision, Blocked or Rejected. Nothing here is implemented by the research sessions.

How to use this page.

Options are mutually exclusive where stated. Effort is a rough build estimate for one session, not a promise.

S-01 Publish a rights decision record for data: which provider, which contract clause, which fields, which territories, which retention. A: licensed provider covering betting use — unblocks everything, costs money and negotiation time. B: private non-commercial research only — cheap, still bars picks and any public numbers. C: no data — the site stays an evidence shell. Mixed A+B is impossible to display safely, because the display itself is the restricted act. 1 session plus legal review Needs a decision NBA.com Terms §9
NBA Stats FAQ
S-02 Add a data-source matrix page: every required input, its owner, refresh cadence, timestamp field, correction policy and permission status. A: one table per input type (schedule, box score, lineup, injury, price, settlement). B: single flat table — faster to read, harder to maintain. A is recommended, because permissions differ per field and a flat table hides that. ½ session Proposed NBA injury report policy
S-03 Add an immutable forecast ledger schema, so every future line is stored with model version, input snapshot IDs and issue time before the event. A: append-only JSON/CSV with a hash per record. B: database table with version rows. Both are static-hostable if written at build time; A is simpler and diffable in Git, B needs a backend the current host cannot run. 1 session (schema only) Proposed scikit-learn: time-series validation
S-04 Turn the validation gates into a pass/fail scorecard with an explicit “first failing gate” column. A: binary pass/fail per gate. B: pass/fail plus a distance-to-threshold. B risks implying partial credit for an unvalidated model, so A is recommended until real data exists. ½ session Proposed scikit-learn: metrics and scoring
S-05 Pre-register the leaderboard rules (objective, baselines, holdout, tie-breaks, reward terms) as a dated, versioned document before any model is scored. A: preregister now, reward-free. B: wait for data then preregister — risks rules being fitted to results. A is strongly preferred; the whole point is that rules precede results. 1 session Needs a decision scikit-learn: proper scoring rules
S-06 Add a correlation worksheet: leg pair, conditioning set, estimator, sample count, game-clustered interval, shrinkage rule. A: residual Pearson for continuous legs plus joint-frequency for threshold legs. B: one generic coefficient for everything — misleading, because a parlay needs a joint probability, not a linear association. A is recommended. ½ session (template only) Proposed NIST: correlation definition
NIST: bootstrap uncertainty
S-07 Build the injury-to-production chain as four separately validated steps: status, availability, minutes, production. A: four models with separate error reporting. B: one end-to-end model — fewer moving parts, but it hides which step failed and invites treating a status label as an impact estimate. A is recommended. 2 sessions (design), blocked on data Blocked NBA injury reporting policy
S-08 Keep a decision log page: date, question, options, choice, who decided, and what would reverse it. A: a table on this site. B: an ADR folder in the repository. Both are cheap; A is visible to a non-technical reviewer, B is better for versioning. Doing both with A as a rendered view of B avoids duplicate truth. ½ session Proposed NBA4 repository
S-09 Add a staleness banner that flips the whole slate page to “no picks” whenever its newest source timestamp exceeds a declared threshold. A: hard suppression. B: a warning while still showing numbers — rejected, because a stale line that looks current is exactly the failure mode that costs money. ½ session (logic spec only until data exists) Proposed NBA injury report (continual updates)
S-10 Separate “no edge found” from “no data” everywhere a blank appears. A: three states — not computed, computed and excluded, computed and eligible. B: keep one blank state. A is recommended: the current single blank makes a tested-and-rejected strategy look identical to an untested one. ½ session Proposed scikit-learn: calibration limits
S-11 Move commercial or live functionality to permitted hosting if, and only if, the product becomes commercial. A: stay static and informational. B: backend host with secrets and access control. B is required the moment there are accounts, rewards, paid access or live ingestion; the current host cannot serve it. Depends on scope Proposed GitHub Pages limits
S-12 Show a responsible-use and age note beside any future reward or contest content. A: static notice. B: age-gate. B is a compliance decision, not a design one; both belong to legal review for the target jurisdictions. Minutes (copy), gated by review Blocked Ksa: 10 tips for gambling safely

What we still need from you

Facts only you can supply — no source can answer these.

Full question register →
  1. Intended use. Personal research, a public tipster page, or a commercial product with rewards?
  2. Budget for data. Licensed feeds are the gating cost; “free NBA stats” is not an available route.
  3. Jurisdictions. Which countries would see picks, and would any link to a bookmaker?
  4. Risk tolerance for being wrong. Whether a silent “no pick” is acceptable, or whether you need a measurable pipeline even before it is profitable.
  5. Timeline. Whether a correct empty dashboard now beats an attractive but unvalidated one later.
